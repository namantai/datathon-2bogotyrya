## 1. Миссия и источник требований

Создаём **работающий локальный AI-сервис анализа видеозаписей кассовых операций** для ForteBank. Пользователь загружает новую запись `.mov`; сервис анализирует визуально наблюдаемые действия и сообщает, есть ли **признаки возможных нарушений**, а также показывает тип события, точный таймкод, 1–3 кадра-доказательства, краткое объяснение и нормативный источник Республики Казахстан. Сервис работает через веб-интерфейс **и** API жюри.

Источник истины — ТЗ **«Техническое задание Datathon 26»**, включая FAQ и раздел 10. Если оно доступно, сверяй с ним соответствующие изменения. О расхождениях с этим файлом **сообщай, не решай их молча**. Отличай требования организаторов от командных решений.

**Не гарантируй 100/100:** скрытые тесты неизвестны; измеряй качество честно.

Для облачного Codex — **только синтетика/заглушки**. Спорные варианты (Colab, внешний туннель с передачей видео) — только после согласования с организаторами.

6. Не делай выводов, требующих невидимых данных (АБИС, проводки, журналы). Результат — **подсказка человеку**, не окончательный юридический вывод.
7. Только модели, веса и зависимости с **проверенной коммерчески разрешающей лицензией**. Проверяй лицензии кода и checkpoint **отдельно**, включая ограничения/notices; сомнения согласуй до внедрения.
8. По FAQ готовые предобученные open-source модели/шаблоны разрешены при подходящей лицензии, но использование «готовых решений» названо основанием дисквалификации. Не выдавай сторонний законченный сервис за разработку команды.
9. **Не коммить** видео, кадры, разметку, веса, ключи, `.env`, локальные базы, артефакты или чувствительные логи. `data/`, `weights/` локальны; корневой `.gitignore`; `.env.example` без секретов.
10. Не раскрывай `X-API-Key` во frontend JavaScript, в Git, в сообщениях об ошибках или логах. Для UI продумай безопасный серверный путь к API (например, same-origin backend/proxy), не меняя контракт жюри.

## 4. Обязательный сценарий пользователя

1. Открыть веб-интерфейс и загрузить новое `.mov` видео.
2. Увидеть статус обработки, пока локальная модель работает.
3. Получить **ровно один** из вердиктов: «Нарушение не обнаружено» / «Обнаружены признаки возможных нарушений».
4. При наличии событий увидеть **каждое** событие с типом, таймкодом, описанием.
5. Увидеть **1–3 реальные JPEG-кадра-доказательства** из соответствующего фрагмента.
6. Прочитать короткое описание **наблюдаемых фактов**, без неподтверждённых предположений.
7. Увидеть название документа и пункт/раздел, если подтверждён, вместе с доступной ссылкой на источник.
8. Передать видео в обязательный API жюри и получить результат без ручного запуска кода.

FAQ: ≥40 постановочных `.mov`, 10–145 с, от 29 FPS, ~29 МБ, без звука; одна верхняя камера, кассир/клиенты/инкассаторы. Разметка: факт нарушения и таймкод, **без типа**. Тест: ≥5 видео, возможны другой ракурс и неизвестные классы. Параметры train **не превращать в жёсткие лимиты загрузки**. «Нарушения по бездействию» требуют временного контекста.

## 5. Неизменяемый API-контракт жюри

**Авторизация:** заголовок `X-API-Key` для обоих маршрутов; неверный или отсутствующий ключ отклонять.

- `POST /api/v1/analyze`: `multipart/form-data`, поле **`file`**, вход `.mov`; быстрый ответ с **`job_id`**, запуск обработки отдельно от HTTP-запроса.
- `GET /api/v1/jobs/{job_id}`: вернуть статус **`processing`**, **`done`** или **`failed`**; при `done` вернуть результат.
- Значения `verdict` **строго** `no_violation` и `violation`. Третьего вердикта (`unknown`, `insufficient_data` и т. п.) в официальной схеме **нет**.
- При `no_violation` массив `violations` должен быть **пустым**. При обнаружении нескольких событий вернуть несколько элементов без дублирования одного события.
- В каждом событии обязательны `type` (строка), `timecode_sec` (число, секунды от начала видео), `description` (наблюдаемые факты и осторожное объяснение), `evidence_frames` (от **1 до 3** элементов), в каждом кадре — `timestamp_sec` (число) и `image_base64` (JPEG в base64).

Ожидаемая форма завершённого ответа:

```json
{
  "job_id": "example-job-id",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Проверенный тип возможного нарушения",
      "timecode_sec": 44.2,
      "description": "Что действительно видно и почему событие требует проверки",
      "evidence_frames": [
        { "timestamp_sec": 44.2, "image_base64": "BASE64_JPEG_BYTES" }
      ]
    }
  ]
}
```

**Не меняй пути/поля/типы/enum.** Новые публичные поля — только после согласования. В UI обязателен нормативный источник, хотя JSON-пример ТЗ **не содержит отдельного поля для него**: храни нормативную связь внутри сервиса/UI, не ломая схему жюри.

**Лимит — 5 минут:** отсутствие результата/доступности засчитывается как необработка. Измеряй end-to-end на целевом оборудовании (очередь, декодирование, inference, ответ), оставляй запас.

## 6. Нормативы и проверяемость вывода

- Основная юрисдикция — **Республика Казахстан**: действующие акты НБРК и тексты на `adilet.zan.kz`. Открытые документы других банков допускаются FAQ, но **не называй их нормативными актами РК**.
- Список классов **не дан организаторами**. Классы вводи после просмотра роликов и проверки визуальной наблюдаемости и правового основания; не фантазируй закрытый список.
- Для каждого правила храни: стабильный `rule_id`, видимое действие, требуемый контекст, исключения, название документа, URL, пункт/раздел (если подтверждён), дату/редакцию проверки, ограничения интерпретации.
- FAQ допускает ссылку без точного пункта; **не выдумывай номер**. Проверяй актуальность. Непроверенный источник явно помечай.
- Пиши о **возможных признаках**, не о юридическом приговоре; «не видно» ≠ «не было».
- Для нарушения по бездействию анализируй весь необходимый временной контекст и выбирай доказательный таймкод осмысленно; если событие невозможно подтвердить по видео, не изображай его подтверждённым.
- Кадры-доказательства должны соответствовать **оригинальным кадрам данного ролика** и переданным временным меткам. Не используй сгенерированные, чужие или не относящиеся к событию изображения как доказательства.

## 7. Архитектурные границы и контракт между участниками

Планируемые области (сначала изучи реальную структуру, не перестраивай её без согласования):

- **`backend/` (Fullstack):** FastAPI, API-key, загрузка/проверка `.mov`, фоновые задания, статусы, локальное хранилище, сборка JSON, кадры-доказательства, интеграция.
- **`frontend/` (Fullstack):** загрузка, статус, два вердикта, список событий, кадры, ссылки на правила, обработка ошибок.
- **`ml/` (ML Engineer):** декодирование/выборка кадров, датасет/разметка, признаки, fine-tuning, локальный inference, временная локализация, оценка качества.
- **`configs/` (совместно):** согласованная карта правил и категорий.
- **`docs/` (совместно):** контракты, нормативы, эксперименты, лицензии, запуск, ограничения.

**Внутренний ML-контракт** отличается от API жюри: например, `analyze_video(local_video_path) -> list[Event]` с `class_id`, `start_sec`, `end_sec`, `timecode_sec`, внутренним confidence, `observation`, `rule_id`, метками кадров. Оба участника утверждают окончательную схему в `docs/ml-contract.md`.

- ML не изменяет HTTP-схему жюри; Backend не изменяет без согласования обучение и модельные классы; Frontend не выдумывает предсказания/ссылки.
- Для ранней разработки Backend разрешён **явно помеченный FakeAnalyzer только в dev/test**. Нельзя оставлять заглушку или константный вердикт в production и выдавать это за AI-анализ.
- Не добавляй лишний микросервис, брокер, базу данных, Docker-слои или тяжёлые зависимости без реальной необходимости. Простота, устойчивость и воспроизводимость важнее модной архитектуры.

## 8. ML: обязательная дисциплина экспериментов

1. **Не обучаем с нуля.** Рассматриваем дообучение разрешённых pretrained-моделей. X-CLIP — кандидат для сравнения, а не заранее доказанное лучшее решение; объектный детектор добавляй только после анализа конкретных ошибок.
2. Перед обучением **просмотреть датасет**, каталогизировать видео и разметить наблюдаемые действия/типы/временные интервалы. Документировать спорные случаи и негативные примеры.
3. Train/validation/test делить **по целым видео и по возможности по сценариям/людям**, не по соседним кадрам; не подбирать пороги на holdout.
4. Сначала baseline, потом fine-tuning. Сравнивать на одинаковых разбиениях; сохранять seed, config, checkpoint, метрики и latency.
5. Измерять **video-level** precision/recall/F1 и FP/FN, качество по классам, временную ошибку, релевантность кадров, latency на целевом оборудовании и ошибки под другим ракурсом. Маленький тест не доказывает 100% качество; не фабрикуй метрики.
6. Возможность нескольких событий обязательна. Для событий не путать совпадение классификации целого видео с точной локализацией. Предпочитай анализ временных окон/последовательности при необходимости.
7. Пороги: по FAQ **минимум ложных срабатываний, пропуск недопустим**. Честно измеряй компромисс и ограничения.
8. Не делай зависимость от координат одного фиксированного ракурса без проверки переноса. Проверяй изменение освещения, частичное перекрытие, длину, FPS, поворот/ориентацию и другой ракурс. При преобразовании видео сохраняй правильные временные метки.
9. Запрещён `train` на тестовых видео жюри; нельзя использовать их даже для переобучения/настройки после отправки API-запроса.

## 11. Критические тесты перед сдачей

**Контракт и безопасность:** правильная загрузка `.mov` через поле `file`, правильный `job_id`, все 3 статуса, 2 значения verdict, пустой список при `no_violation`, несколько событий, 1–3 валидных JPEG-base64 кадра на событие, корректные float-таймкоды, реальное соблюдение `X-API-Key`; обработка неверного `job_id`, неверного ключа, повреждённого/неподходящего файла; запрет утечки секретов и данных.

**Сквозной сценарий:** загрузка → статус → локальный inference → нормативная интерпретация → доказательные кадры → API JSON и UI, без ручного выполнения Python после загрузки. Проверить публичный URL **из другой сети**, а не только `localhost`.

**Качество:** здоровые отрицательные примеры, неизвестные записи, несколько нарушений, ошибочные/неопределённые наблюдения, новые ракурсы, реальные таймкоды, невыдуманные обоснования, сравнение с ручной разметкой.

**Производительность и переносимость:** максимальные и типичные ролики, замер 5-минутного лимита, контролируемая конкуренция заданий и потребление GPU/RAM, локальная обработка после отключения интернета, загрузка всех весов из локальных путей.

**Эксплуатация:** понятная инструкция запуска, воспроизводимая установка зависимостей, корректная очистка временных данных, неразрушительный restart, известные ошибки задокументированы. При отсутствии реального оборудования/данных явно отмечать непроверенные проверки.

- Список поддерживаемых типов возможных нарушений и их визуальных признаков.
- Нормативные источники и описание связи «правило ↔ событие ↔ кадр».
