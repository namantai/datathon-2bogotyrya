# Серверный бюджет, ML-граница и нормативное сопоставление

Это подготовка Fullstack, не завершённая интеграция настоящей модели. Официальные
API жюри, X-API-Key и JSON не изменены. Новые сведения доступны опционально в
существующем закрытом UI-маршруте. После комплексного ревью Frontend запрашивает
`include_details=true`: различает server timeout, показывает предварительный риск
Backend и только проверенные применимые нормативные кандидаты. Старые ответы без
метаданных остаются совместимыми; неизвестный риск не выдумывается.

## Три разных времени

1. Frontend: 300 секунд от нажатия «Начать анализ», включая загрузку и polling.
2. Backend: `APP_JOB_TIMEOUT_SEC=300` от входа запроса в ASGI, до разбора multipart.
   Включает авторизацию, приём файла, валидацию, очередь, локальный анализ,
   извлечение кадров, сопоставление и подготовку результата.
3. Дополнительный предел `APP_ANALYSIS_TIMEOUT_SEC=240` начинается при запуске worker,
   но не даёт новый бюджет: используется минимум из него и остатка (2).

SQLite хранит UTC Unix-времена получения, принятия в очередь, запуска, дедлайна
и завершения; `total_duration_sec` — от получения запроса Backend.
Для исполнения дедлайна используется монотонный таймер, не клиентский timestamp.
Миграция добавляет поля без удаления таблицы; старым строкам для диагностики
присваивается `created_at + 300`. Незавершённые старые задания по-прежнему становятся
`failed` при restart; не возобновляются.

Ожидающее задание истекает даже без polling, удаляя своё видео. Активная работа
отменяется с оставшимся бюджетом; терминальное `failed` не перезаписывается поздним
результатом. Timeout до регистрации даёт HTTP 408 без `job_id`; после регистрации —
публичный `failed` и внутренний `analysis_timeout`. Нет третьего verdict или
успешного отрицательного результата по тайм-ауту.
Результат/нормативные детали сохраняются атомарно в строке и переживают restart;
анонимные UI-сессии по-прежнему сбрасываются при restart.

Ревью дополнительно закрыло окно позднего успеха: дедлайн проверяется после
сериализации JPEG/base64 JSON и внутри транзакции сохранения; запоздавшая запись
откатывается. Уже истёкший бюджет после приёма файла отклоняется до регистрации,
даже если валидатор завершается синхронно. UI использует `performance.now()` и
повторную проверку дедлайна после ответа, а не только callback таймера.

Логи содержат состояние, длительность и безопасный тип ошибки, не видео, наблюдения,
base64, ключи или traceback модели. Срок хранения JSON/JPEG и нормативных деталей
одинаковый: существующая настраиваемая retention-политика.

### Чего таймер не гарантирует

Backend не знает момент клика. Транспорт до получения запроса, буферизация reverse proxy
и доставка/показ ответа находятся вне его часов. Переданным клиентом абсолютным часам
не доверяем. Полный SLA от клика нельзя подтвердить серверным таймером без клиентских
измерений. Обязательный заголовок/поле жюри не добавлен: совместимое решение — два
явно разных отсчёта + UTC-метаданные для будущей синхронизации UI.
SLA нужно измерять с реальной моделью на целевом оборудовании, с очередью, холодной
загрузкой весов, upload и polling, оставляя запас до 300 секунд.

Async-адаптер обязан реагировать на отмену. Новая process-граница принудительно
завершает child; FFmpeg/FFprobe уже поддерживают отмену. Синхронная блокировка event
loop, зависший диск/SQLite или неотменяемый kernel I/O не имеют real-time гарантии.
SQLite сохраняет busy timeout 5 секунд. Это ограничение, а не подтверждение SLA.
Job budget нельзя увеличить выше 300, но можно снижать для эксплуатационного запаса.

## Приватное расширение существующего UI GET

`GET /ui-api/jobs/{job_id}?include_details=true` возвращает прежние поля плюс:

- `timing.server_time`, `request_started_at`, `accepted_at`, `processing_started_at`,
  `deadline`, `completed_at`: UTC ISO 8601; неизвестные времена — null;
- `timing.duration_sec`: конечная длительность, до завершения null;
- `timing.budget_scope = "backend_request_not_browser_click"`;
- `failure_reason`: `timeout`, `processing_failed` либо null, без внутренних исключений;
- `event_details`: массив по индексам `violations`; код, название, предварительная
  severity, версии определения/каталога, статус и нормативные кандидаты.

Без параметра старые клиенты получают прежний JSON. В официальном API жюри параметр
ничего не добавляет. Обязательны cookie-сессия и владение job_id; Origin/Fetch Metadata
сохраняются, CSRF обязателен на изменяющих запросах. Чужое задание — 404, отсутствие
сессии — 401, ответы `Cache-Control: no-store`. Публичных маршрутов кадров нет.

## Каталог и алгоритм

Runtime-каталог — `backend/src/fortebank_api/rule_catalog.json`, package data Backend,
в том числе для Docker. Pydantic валидирует его при старте. Новая БД/сервис не нужны.
`rules.py` проверяет уникальность, ссылочную целостность и HTTPS; `verified` требует
реквизитов проверки. Runtime не обращается в интернет.

Каталог содержит определения событий, документы и many-to-many соответствия.
Пять примеров из задания — draft-кандидаты, не перечень классов, уже распознаваемых
моделью. Риск `undetermined`: без регламента не назначаем «критическое нарушение».
Риск — внутренний приоритет, не юридическая ответственность.

`RuleEngine.candidates(code)` ищет все соответствия. `assess(code, conditions)`:

- неизвестный код → `unknown_event`, событие не теряется;
- известный код без связи с источником → `missing_source`;
- установленное условие противоречит правилу → `not_applicable`;
- не хватает условий → `insufficient_data`, перечень недостающих условий,
  предварительный источник и его собственный review-status;
- условия есть, но каталог/привязка не проверены → `requires_review`;
- всё проверено и условия соблюдены → `candidate`, всё равно нужна оценка специалиста.

Условия — строгие boolean; отсутствует ≠ false. Confidence модели не заполняет
неизвестные условия и не повышает статус юридической проверки. `rule_id` из ML
не выбирает источник, произвольные нормативные URL от ML не принимаются.
Публичное `description` сохраняет наблюдение; юридические пояснения отдельно.
«Недостаточно данных» — о применимости нормы, **не новый verdict жюри**.

## Проверенность источников на 2026-10-18

Официальная карточка: [Правила № 231](https://adilet.zan.kz/rus/docs/V1900019680).
Индекс официального источника подтверждает реквизиты № 231 от 29.11.2019 и название.
Полный актуальный текст через используемый доступ не получен: основная страница
требует JavaScript, legacy-страница не ответила.
**Ни один нормативный пункт в этом изменении не отмечен юридически проверенным.**

Пункт 20 — кандидат из задания (`candidate_provision`); подтверждённый `provision`,
содержание требования, редакция и дата проверки — null. Связь с CASH_UNSECURED —
`pending_review`. Требуется отдельно установить принятие наличных, назначение места
хранения и применимость операции; расположение наличных в кадре этого не доказывает.

Нужно проверить действующую редакцию Правил № 231 и п.20, исключения и область
применения; получить от банка правила хранения/закрытия сейфов, доступа к дверям,
замещения кассира и проверки документов. Внутренние регламенты ForteBank не выдуманы.
До `verified` необходимы согласование классов/условий с ML Engineer и проверка
специалистом по нормативам.

## Проверка

Backend: `.venv/bin/python -m pytest`, `.venv/bin/python -m compileall -q src tests`,
`.venv/bin/python -m pip check`. Новые тесты: `test_deadlines.py`, `test_rules.py`,
`test_local_analyzer.py`; только синтетика, короткие реальные таймеры вместо ожидания 300 с.
Сохранены прежние API/security/evidence/SQLite/Docker regression-тесты.
Frontend: `npm test`, `npm run typecheck`, `npm run build`, `npm run test:production`.
Из корня: `git diff --check`.

Вручную: на изолированном local fake-стенде загрузить синтетику, получить `job_id`,
запросить обычный и расширенный UI GET в той же сессии. Для timeout временно снизить
`APP_JOB_TIMEOUT_SEC`; повторные GET должны сохранять `failed` и `failure_reason=timeout`,
а не `done/no_violation`. Вернуть настройку. Другой браузерный профиль не должен читать
результат; API жюри без ключа — 401. Реальную модель подключать только по
[ML-спецификации](ml-contract.md) после проверки лицензий.
