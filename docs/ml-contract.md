# Внутренний контракт Backend ↔ ML

Статус: реализован бинарный MVP-адаптер `LocalMLAnalyzer`. Мультиклассовые события
и нормативная карта остаются неподтверждёнными. Публичная схема жюри не меняется.

Документ предлагает минимальную границу интеграции и не задаёт архитектуру модели, конкретный framework или список классов нарушений.

## Предложенный интерфейс

```python
def analyze_video(local_video_path: Path) -> AnalysisResult:
    ...
```

Backend использует `async Analyzer.analyze_video(Path) -> AnalysisResult`. В режиме
`local` он вызывает `VideoAnalyzer.predict(str)` через `asyncio.to_thread`, сериализуя
вызовы. Backbone и head загружаются один раз при lifespan startup. Standalone
`ml.inference.analyze_video(str) -> list[dict]` сохранён. `predict` использует тот же
детектор, но возвращает метки для backend-owned evidence вместо сохранения JPEG.
При cancellation адаптер дожидается завершения native thread, прежде чем разрешить
удаление исходника. Это cooperative timeout, не принудительное завершение Torch.

`local_video_path` указывает на локально сохранённый и предварительно проверенный Backend файл. ML-модуль не должен загружать его во внешние сервисы или читать аудио.

## Предложенные структуры

```python
@dataclass(frozen=True)
class Event:
    class_id: str
    start_sec: float
    end_sec: float
    timecode_sec: float
    confidence: float
    observation: str
    rule_id: str | None
    evidence_timestamps_sec: list[float]


@dataclass(frozen=True)
class AnalysisResult:
    events: list[Event]
```

Семантика полей:

- `class_id`: стабильный внутренний код согласованного класса; неизвестные классы сейчас не фиксируются.
- `start_sec`, `end_sec`: границы события в секундах от начала исходного видео.
- `timecode_sec`: наиболее доказательный момент события.
- `confidence`: внутренний score `0..1` (максимум сглаженных sigmoid scores);
  **не калиброванная вероятность**, в публичный JSON не включается.
- `observation`: краткое описание только видимых действий, без юридического приговора.
- `rule_id`: ссылка на согласованную карту правил, а не произвольный нормативный текст модели.
- В бинарном MVP `class_id="possible_violation"`, `rule_id=None`: конкретное действие
  и правовое основание модель не установила. Текст фиксированный, с просьбой ручного
  просмотра; визуальные действия/типы не генерируются. Для других классов backend
  по-прежнему требует непустой rule ID. UI уже показывает отсутствие источника.
- `evidence_timestamps_sec`: 1–3 конечные неотрицательные метки в пределах исходного видео, по которым Backend извлекает реальные JPEG-кадры. Публичный `timestamp_sec` кадра может немного отличаться: Backend возвращает фактический PTS выбранного декодированного кадра, а не копирует запрос ML.

Для local-адаптера соблюдается `0 ≤ start_sec ≤ timecode_sec ≤ end_sec < duration`.
Кандидаты объединяются существующим ML postprocessing и сортируются по timecode;
evidence PTS отсортированы, уникальны, находятся внутри события и включают timecode.
Ноль временной шкалы в ML и backend — первый декодированный video frame, не audio
или format start. Реальный backend JPEG может отличаться на межкадровый интервал.
Исключение ML/evidence означает `failed`, никогда успешный отрицательный вердикт.

Конфигурация/ручная оценка описаны в [local-ml.md](local-ml.md). Загрузка checkpoint
использует `weights_only=True`, backbone — только local files и проверку manifest/SHA-256.

`AnalysisResult(events=[])` означает отсутствие обнаруженных событий. Список может содержать несколько разных событий; правила дедупликации требуют совместного определения.

## Ответственность Backend

- проверить и безопасно сохранить входной файл;
- управлять заданием и тайм-аутом;
- вызвать ML-модуль с локальным путём;
- проверить инварианты результата и преобразовать внутренние ошибки;
- извлечь 1–3 реальных кадра по временным меткам;
- связать `rule_id` с проверенными нормативными данными;
- преобразовать внутренний результат в неизменяемый API-контракт жюри.

## Ответственность ML

- выполнить полностью локальный визуальный inference;
- вернуть события с временной локализацией и наблюдаемыми фактами;
- поддержать отсутствие и несколько событий;
- не формировать публичный HTTP-ответ и не придумывать нормативные ссылки;
- не зависеть от фиксированных координат одного ракурса без измеренной проверки.

## Вопросы до утверждения

1. Тип исключений и поведение при недекодируемом видео или внутренней ошибке.
2. Диапазон, смысл и калибровка `confidence`.
3. Инварианты `start_sec ≤ timecode_sec ≤ end_sec` и точность времени.
4. Формат и версионирование `class_id` и `rule_id`.
5. Правила выбора 1–3 кандидатов и дедупликации близких временных меток.
6. Синхронный интерфейс процесса или изолированный worker при измеренной необходимости.
# Дополнение: UI и ручная проверка (18.10.2026)

Logistic v4 выдаёт только `possible_violation`. Критичность автоматического
сигнала — `unverified`, правовая привязка отсутствует. Описание:
«Обнаружены признаки возможного нарушения кассовой дисциплины. Тип события и
нормативное основание требуют проверки.» Это не отдельный распознаватель действий.

Дополнительные оценки каталога доступны только в UI через
`GET /ui-api/jobs/{job_id}?include_details=true`; обязательный ответ API жюри
не изменяется. Авторизованные человеческие наблюдения, степень риска и
предлагаемые нормы хранятся в отдельной истории `human_reviews`, не заменяют
автоматический результат и не используются как обучающие метки.
См. [интеграцию и процедуру проверки](frontend-ml-integration.md).
