# Архитектура проекта

## Цель

Проект строится как один локально разворачиваемый продукт с Web UI, Backend API и локальным ML inference. Простое разделение областей позволяет двум разработчикам работать параллельно без микросервисов, брокера сообщений и отдельной базы данных на стартовом этапе.

## Ответственность компонентов

### Frontend

Frontend отвечает за пользовательский сценарий: выбор `.mov`, отображение хода обработки, одного из двух итоговых вердиктов, списка событий, таймкодов, кадров-доказательств и проверенных нормативных источников.

Ключ жюри `X-API-Key` нельзя передавать в browser JavaScript. На следующих этапах UI должен обращаться к безопасному same-origin серверному маршруту либо к другому согласованному серверному посреднику.

### Backend

Backend отвечает за HTTP API, проверку API-ключа, безопасный приём файлов, жизненный цикл заданий, вызов локального ML-модуля, извлечение исходных JPEG-кадров, нормативное обогащение результатов и сборку ответа по контракту жюри. Публичные поля API не должны зависеть от внутреннего формата ML.

### ML

ML-модуль отвечает за локальный анализ видео, обнаружение и временную локализацию наблюдаемых событий. Он не должен вызывать облачные AI API, идентифицировать людей или зависеть от доступа в интернет во время inference. Реализация, модель и классы находятся в области ответственности ML Engineer.

### Совместные области

- `configs/`: согласованная карта наблюдаемых категорий и нормативных правил.
- `docs/`: публичный API-контракт, DRAFT внутреннего ML-контракта, требования, лицензии и ограничения.

## Взаимодействие

Планируемая последовательность: Frontend передаёт видео через безопасный серверный путь → Backend сохраняет его во временное локальное хранилище и создаёт задание → локальный ML-модуль возвращает внутренний `AnalysisResult` → Backend связывает события с правилами и извлекает реальные кадры → Frontend и API жюри получают представления из одного результата.

Внутренний контракт Backend ↔ ML описан отдельно в [ml-contract.md](ml-contract.md) и остаётся DRAFT до согласования обоими разработчиками. Официальный контракт жюри описан в [api-contract.md](api-contract.md).

## Реализовано на этапе 01

- минимальное FastAPI-приложение;
- технический `GET /health`;
- централизованная конфигурация Backend из окружения;
- автоматический тест health-маршрута;
- стартовое React + TypeScript + Vite приложение;
- базовые правила исключения локальных данных и секретов из Git;
- документация требований и контрактов.

## Запланировано, но не реализовано

- API жюри и проверка `X-API-Key`;
- загрузка и валидация `.mov`;
- фоновые задания и локальное хранилище статусов;
- ML inference и окончательный внутренний контракт;
- извлечение кадров-доказательств;
- карта нормативных правил;
- полный пользовательский сценарий и развёртывание.

Такая архитектура минимизирует операционные компоненты, сохраняет чёткую границу между Fullstack и ML и допускает последующее выделение хранилища или очереди только после появления измеренной необходимости.
